Assembly / Build / Part — a plan for the BOM uploader

A design for teaching ValorBOM the three-tier process the team already uses on the shop floor, so the tool tracks builds the way students actually talk about them — instead of forcing every iteration through a two-tier model that has no room for "which bash bar goes with which robot."

00

Summary

Today ValorBOM understands two tiers: an Assembly (a Jira issue type) and a Part (another Jira issue type), tied to a single OnShape document. That matches the first half of how the team designs — Space City Intake and Manor Intake correctly become two different Assemblies, because they differ in form, fit, and function. It doesn't match the second half: when the 2" bash bar became a 1" bash bar, nothing changed about the assembly, but everything about which parts a student should pull for that robot changed. There's no ticket for that distinction today, no OnShape artifact that represents it, and no screen where a student can even ask the question.

This plan adds Build as a real tier between Assembly and Part. A Build is the specific combination of parts a student actually builds — it gets its own Jira issue, its own OnShape version (or branch, if two builds need to stay alive at once), and its own bill of materials, which can reuse parts from a sibling Build or introduce new ones.

The plan is written for two audiences that already exist on the team and will keep using the same tool for different jobs:

  • CAD students design a part, copy the link to their branch, and paste it in. The uploader should figure out the rest — which Assembly, which Build, which Jira tickets, which OnShape version — asking only for the decisions a person actually needs to make.
  • Assembly students never touch OnShape directly. They open an Assembly in ValorBOM and get a build-by-build bill of materials with the assembly instructions to match — the one place to find out what to grab and how to put it together, for whichever build is on the table.

Because the tool now has to remember relationships that don't live comfortably inside a single Jira field — which parts a Build reuses from its predecessor, and the instruction steps for building it — this plan leans on Jira more deliberately rather than adding a database of its own: issue links for relationships that aren't a simple parent/child, and a couple of structured fields for content Jira doesn't have a native shape for. Sheet 04 covers how.

01

Data model: Assembly → Build → Part, and Revision

The relationship that matters most — and the one today's model can't express — is that a Build owns a bill of materials, not a Part. A Part can appear in more than one Build under the same Assembly, at its own quantity, and a Build can be created by cloning a sibling's parts list and swapping out only what changed.

Space City Intake is one Assembly. Build 1 uses a 2" bash bar; Build 2 uses a 1" bash bar. Both builds share the same left side plate and right side plate — one Jira ticket each, linked into both builds — and each build uses its own revision of the same bash-bar part number, linked into only the build that uses it. A student building the robot needs to know: is this Build 1 or Build 2? Both answers are on the same Assembly.

This is the one structural change everything else in this plan follows from: a Part's parent is its Assembly (for numbering and scoping), but its membership is one or more Builds, each possibly at a different quantity. Jira's native parent/child fields assume a single parent, so Sheet 02 covers the field and link-type changes needed to represent that honestly.

Revision is a second axis, on Assembly and Part only — Build doesn't get one. Not every change to an assembly is big enough to be a new Assembly, but some are bigger than a new Build: the assembly itself gets redesigned, yet it's still recognizably the same assembly. Space City Intake could just as easily have gained a Revision B instead of Manor Intake existing as a wholly separate Assembly — same number, a new ticket, and its own OnShape branch. Its Builds don't start over at 1, though: Build numbering belongs to the Assembly as a whole, not to whichever revision happens to be current, so it just keeps counting from wherever the last revision left off. That's deliberate — a bare "Build 1" has to mean one unambiguous build, not "whichever revision's first build you're thinking of." The same axis applies one level down: the bash bar in the diagram above isn't two different Parts, it's one Part number carried through two revisions.

02

Jira mapping

Part is a custom Jira issue type. Assembly isn't — it's the stock Epic type, renamed to display as "Assembly." That's not a shortcut; it's required. Every Part, every PARTS-project purchase ticket, and now Build all point up to their Assembly through the classic Epic Link field — and on Jira Data Center, that field only ever recognizes the literal Epic type as a valid target. There's no per-project setting to register a different custom type at that level; the hierarchy configuration that allows it is a Jira Cloud-only feature, built on a different architecture than Data Center's. We tried the separate-type route first and confirmed this the hard way (gh.epic.error.not.found on every write once the target wasn't Epic-typed) before settling on the rename. Build joins Part as the second custom type. Two more small additions carry the rest of this plan: a Revision field and link on Assembly and Part, and a many-to-many link replacing the single-parent assumption between Part and Build.

Decided Assembly shares its issue type with General's epics. Renaming Epic to Assembly is instance-wide — the General project's 14 existing epics (unrelated team epics, not assemblies) now display as "Assembly" too. Accepted deliberately: the alternative (a genuinely separate type) breaks Epic Link for every Part and purchase ticket, which is worse. Each project's own screens keep the fields sane — General's epics never got Assembly-specific fields like Revision, since those were only added to HAR's screens.

Status is a real Jira workflow, driven automatically — not typed by hand. This mirrors a pattern already running in the team's Jira: the Parts-purchasing flow walks tickets through New → Request for Purchase → Approved → Sent to VFF → Ordered → Delivered via named transitions, and ValorBOM already fires several of those itself — checking a shipment in moves Ordered → Delivered without anyone touching Jira's UI. Build's workflow is shorter: Cut Version (Draft → Active), Supersede (Active → Superseded), and a global Archive reachable from any of the three. ValorBOM fires the transition itself — cutting a version transitions the Build to Active, and in the same action transitions whichever sibling Build was previously Active to Superseded — so nobody has to remember to flip either one. But because it's a real workflow status, not a value only ValorBOM understands, a mentor can still open the ticket in Jira directly and transition it by hand if something needs correcting, exactly the same escape hatch the Parts workflow already relies on.

Naming convention v3. The trailing letter marks a revision — a new ticket, same number, one step in that identity's history — and it belongs on an Assembly or a Part, never on a Build. Number and revision are independent of each other, and independent across types:

VR27A-1000A Intake — the first revision of Assembly 1000.
VR27A-1000B Intake — its second revision: same number, a new ticket, its own OnShape branch — but Builds keep counting from wherever Revision A left off (Build 3, not Build 1 again).
VR27B-2087 Intake Build 1 — a Build, linked up to whichever Assembly Revision ticket it belongs to.
VR27P-3005A Bash bar / VR27P-3005B Bash bar — two revisions of the same Part slot, each its own ticket, each linked into only the one Build that uses it.

A ticket with no revision letter yet is implicitly Revision A — nothing changes for the majority of Assemblies and Parts, which only ever get revised once, or not at all. The letter starts mattering the moment a second revision exists, and even then it's the Revises link, not the letter by itself, that makes the history actually navigable.

Migration. Every existing Assembly and Part ticket becomes Revision A of itself — a field default, no new ticket, no Revises link needed since there's nothing before it. Every existing Assembly additionally gets one implicit Build 1 issue, and every Part currently linked to that Assembly gets the new is used in link added to Build 1. Nothing already in Jira is deleted, renumbered, or relettered.

03

OnShape mapping

A Build is committed to OnShape as a version — an immutable snapshot of the workspace at the moment the team locks in that BOM. A Revision is the bigger step: it forks its own OnShape branch — a new workspace split off from wherever the design diverged — so the prior revision's workspace and version history stay exactly as they were, fully inspectable, while the new revision moves forward on its own. Builds within a revision are just versions cut inside that revision's branch; sibling builds never need a branch between them, since they already share that branch's history up to whichever point each was versioned.

Metadata round-trip, two layers. The client already has updatePartMetadata and updateElementMetadata wired up from the last refactor, but nothing calls them yet. This plan puts them to work in two ways on the same call:

  • Identity, for ValorBOM. The first time the uploader creates a Jira Part for an OnShape element, it writes that Part's key, its Assembly key, and its current Build key back onto the element as custom properties. The next time anyone pastes a link to that same element — even after a rename — the uploader recognizes it by property, not by guessing from the name.
  • Number and Revision, for anyone browsing OnShape directly. Every OnShape element already has native Part number and Revision fields — plain editable text, shown in the Properties dialog and every BOM table by default, confirmed against the team's own reference document (VF27A-0000A: Part number 0000, Revision A). ValorBOM writes the bare number and letter into these on every save, so the BOM table and Properties dialog read the same identity Jira shows — not just an opaque internal id. Jira stays the authoritative source; this is a one-way mirror, not a second place revision can be set from.
04

State & sync

ValorBOM today holds no state of its own — every page load re-derives everything from a live JQL query and a live OnShape BOM read. A Part belonging to more than one Build, and a Build carrying its own instructions, both look at first like they need somewhere new to live. They don't: Jira already has the right native mechanisms for both, once Build and Part lean on more of what a Jira issue can hold than a single custom field.

  • Which parts a Build uses. The is used in issue link from Sheet 02 — native, many-to-many, nothing to build.
  • How many of each. Stays the Part ticket's existing Quantity field, same as today. The one thing this doesn't cover: a Build needing a different quantity of an otherwise-unchanged part. That's a deliberately accepted gap, not one this plan tries to close — see Sheet 09.
  • OnShape version and branch. Already plain Jira fields on Build (Sheet 02) and on Assembly/Revision (the documentId/workspaceId/elementId fields the app already has today) — one workspace id per revision, nothing new invented.
  • Assembly instructions. The new Instructions Data field on Build (Sheet 02), holding the ordered steps as a JSON blob the Hub UI reads and writes structurally. Step images are ordinary Jira attachments on the Build issue, referenced by attachment id inside that JSON — not a new storage system, just a field Jira already supports put to a more deliberate use.
  • Who changed what, when. Jira's own issue history — every field, link, and status change is already tracked per issue. Nothing extra to log.

The sync rule. The existing fix that stops a CAD re-sync from clobbering Jira-only fields like powdercoat and thickness (each write only touches the fields it owns) extends in both directions: Jira writes never overwrite OnShape-authored geometry properties, and OnShape writes never overwrite Jira-authored ticket fields. Every sync is a merge of owned fields, never a full overwrite.

Decided No separate database. Jira already holds everything this plan needs: issue links for relationships, a structured field for instructions, a real workflow for Build status, native history for audit trail. Standing up a second system to hold a few megabytes of JSON wasn't worth the extra thing to run and back up. The one trade-off, accepted deliberately: a Part's quantity is a single number on its own ticket, not a number per Build it's used in — see Sheet 09.
05

Designer tab — the CAD student flow

The portal's navigation collapses to two tabs — Designer and Assembly — replacing today's single /assembly page with a home built for each kind of student. This sheet covers Designer; Sheet 06 covers Assembly.

The student's job stays exactly as small as it is today — paste a link — and the uploader carries the rest, asking only at the two points where a person actually has to decide something: whether this is a brand-new Assembly, and which Build the part belongs to.

  1. Paste the link. Same single input box the tool has today; nothing new for the student to learn to get started.
  2. Confirm, only for a new Assembly. If the uploader can't find this document linked to any existing Assembly, it proposes a name and number and shows a confirm dialog before creating the Jira epic — a deliberate click, not a silent auto-create, so a stray paste doesn't spawn a duplicate epic.
  3. Pick a Build. A row of Build cards under the Assembly — Draft and Active, with status chips — plus + New Build, which can start from a blank BOM or clone a sibling Build's parts list as a starting point (exactly the "keep the plates, swap the bash bar" case).
  4. Preview & diff. The existing New/Exists/Changes table, now scoped to the chosen Build, with a "shared with Build 1" indicator on rows that already exist elsewhere under the Assembly — reusing a ticket instead of minting a duplicate.
  5. Fill in part data, right there in the table. Every "New" row is a real part number about to be minted, not a placeholder — material, machinery, powdercoat, thickness, quantity are all editable inline before saving, so a designer leaves with a fully-specified Part ticket, not a bare number to be filled in later by someone else.
  6. Save. Creates or updates Part issues, links them to the Build, and stamps the OnShape element with the resulting keys.
  7. Cut the version — separately, on purpose. A Build can be saved to many times while still Draft; cutting an OnShape version is its own explicit action, so a build isn't versioned on every small edit. ValorBOM transitions the Build to Active the moment it's cut, and in the same action transitions whichever sibling Build was previously Active to Superseded — two Jira workflow transitions, fired automatically, not two things a person has to remember.
Scope note Starting a new Revision isn't part of this flow. Pasting a link only ever resolves to an existing Revision or proposes a brand-new Assembly — revising an assembly is a bigger call than picking a Build, so it lives as its own deliberate action on the Assembly tab (Sheet 06), never something inferred from a casual paste.
06

Assembly tab — the one-stop shop

Assembly students don't paste OnShape links; they need to know what to grab and how to put it together. A new page, /assembly/:key, replaces today's single flat parts table with a hub built around the thing they're actually deciding: which build.

  • Revision selector. Only shows up once an Assembly has more than one Revision — most never do. When it's there, it's a simple switcher above the Build tabs; the rest of the hub scopes to whichever Revision is selected.
  • Build tabs. One tab per Build under the selected Revision, each carrying its status chip — Draft/Active/Superseded/Archived, a real Jira workflow ValorBOM drives automatically (Sheet 02). There's always exactly one Active tab per Revision, so it doubles as "the one to grab" without a separate flag anyone has to set.
  • Bill of materials. Per-build parts list — quantity, material, machinery, powdercoat, thickness — pulling shared parts in once even though they're also used by a sibling build.
  • Move or re-create, part by part. When the team moves from one Build to the next, each BOM row gets two explicit actions: Move to this Build links the same Part ticket into the new Build — the right call when nothing changed, like the side plates — and Re-create for this Build clones it into a new revision, linked only to the new Build — the right call when it did, like the bash bar. Neither happens silently; a part linked into two Builds was put there on purpose, not left over by accident.
  • Current-build indicator. A Part linked into more than one Build shows which is current — its highest-numbered linked Build — with earlier ones listed as history, so a BOM row is never ambiguous about which build it actually belongs to today.
  • Clone a part. For a part the assembly side needs that never touched CAD — a spare, a second copy of a fastener plate — duplicate an existing Part's data into a new, unrelated ticket (same material/machinery defaults, new number) without a round trip through Designer. Unlike Move/Re-create above, this doesn't create a new revision of anything; it's a fresh Part.
  • Part management. Edit a Part's quantity, material, machinery, powdercoat, or thickness directly from the hub — the same fields Designer can set, available here too, since not every correction should require going back to OnShape.
  • OnShape version link. One click from the BOM straight into the exact OnShape version that build was cut from.
  • Assembly instructions. An ordered list of steps, each a short line of text plus an optional photo or diagram and an optional reference to a specific part and quantity — authored once per build, stored in the Build issue's Instructions Data field (Sheet 04), with an optional plain-text copy synced into the Jira Build issue's description for anyone without portal access.
  • Print view. A clean, printable page per build — parts list plus steps plus images — built on the print-aware styling the app already has, meant for the pit table.
  • Build comparison. A side-by-side of two builds' BOMs, so "which bash bar do I grab" has a direct answer instead of a guess from memory.
07

Part lifecycle & in-product guidance

Both tabs are used by high schoolers, most of whom will touch ValorBOM for one season. The UI has to carry the explanation itself — where a Part is in its life, and what the four words on screen (Assembly, Build, Part, Revision) actually mean — rather than pointing to a wiki page nobody reads before the first regional.

"Active" isn't exclusive to one Build — a Part moved forward into a later Build (Sheet 06's Move to this Build) just adds that Build to the same ticket, and the current-build indicator shows whichever is latest. Superseded means something more specific: a different ticket — a new revision made with Re-create for this Build — took its place for the newer Build, and this one stays exactly as it was for the Build it actually shipped in.

A Build gets the same treatment one size up: its Draft Active Superseded Archived chips are a real Jira workflow status (Sheet 02), driven automatically the same way the team's existing Parts-purchasing flow already drives Ordered/Delivered — so the chip a student sees can't quietly go stale, but a mentor can still correct it by hand in Jira if something needs fixing. An Assembly adds only the Revision letter underneath. Three tiers, one visual language.

In-product guidance, not a manual.

  • One vocabulary, everywhere. Jira-native terms — Epic Link, issue type, custom field — never surface in the student-facing UI. Only the four words the team already uses out loud: Assembly, Build, Part, Revision.
  • Inline glossary. A small "?" beside any of those four words, anywhere they appear, opens a one-sentence, plain-language definition on the spot — not a link out to Confluence.
  • Teaching empty states. Before an Assembly has a second Build, the + New Build control's helper text explains what a Build is using the team's own example ("same assembly, different combination of parts — like a 1" vs. 2" bash bar"), right where a student is about to create one.
  • Confirm dialogs explain the stakes. The new-Assembly and new-Revision confirm gates (Sheets 05–06) say in plain terms what's about to happen and why it matters, not just "Are you sure?"
08

Rollout phases

Ordered so each phase produces something usable on its own, rather than one large cutover.

  1. Phase 0

    Jira schema Done

    Build issue type and its fields (Build Number, Onshape Version Link, Instructions Data), its own workflow (Cut Version/Supersede/Archive), the Revision field on Assembly and Part, and the Used In / Revises link types — all shipped. Assembly ended up as the stock Epic type renamed, not a new type (Sheet 02); Build has its own dedicated workflow, split off from the one Part shares.

  2. Phase 1

    Backend foundations Done

    BuildService (continuous build numbering across a revision chain, cutVersion driving Cut Version/Supersede automatically, Archive) and RevisionService (walks the Revises chain, advances the revision letter); createVersion/listVersions/createBranch on the OnShape client (the branch request body is a best guess, flagged in the code for verification against Onshape's own API Explorer); createIssueLink on the Jira client; the one-time migration script, dry-run by default. 23 new tests, all passing. Not yet wired to any route — Phases 2 and 3 are what actually call this.

  3. Phase 2

    Designer tab Done

    Shipped the flow from Sheet 05 end to end: AssemblySelection reused as-is for the Assembly step; a new BuildSelection picker (dropdown plus create, with an optional clone-from-sibling); a new DesignerPartsTable that merges the Assembly-wide CAD preview with the Build's own linked-part list client-side, so an existing Part shows as reusable ("from another build") alongside the usual New/Changes rows, plus a Cut Version action wired to the real OnShape orchestration. PartRow grew two optional, backward-compatible props rather than forking it — the Assembly BOM page's table is untouched. Verified via a clean vite build and the full Jest suite (416/416); no browser-automation tool was available this session to click through it directly, so that pass is still owed before calling the UI itself trustworthy, not just its build.

  4. Phase 3

    Assembly tab Done

    Shipped: a new /assembly/:key page — Revision selector (only when a chain exists), Build tabs carrying the real status chip, and a per-build BOM that pulls in every Part linked across the Revision's sibling Builds, not just the active one. A row already in the active Build is directly editable (same fields Designer sets); a row that only belongs to a sibling renders as a candidate with the two explicit actions from Sheet 06 — Move to this Build (plain link) and Re-create for this Build (a real new Part revision via RevisionService, chained with Revises, linked only to the new Build). The current-build indicator is derived client-side from each part's full linked-build set rather than a separate query per part. Cut Version and Archive are one click from the hub itself. New backend surface: BuildService.getBuildsForPart, BuildService.recreateForBuild, PartService.getStoriesByKeys, EpicService.getEpicByKey, and the Revises-chain endpoint that Phase 1 had built but never routed. Clone a part shipped too: the team decided ValorBOM should allocate its own number rather than requiring a manual entry — PartService.getNextPartNumber finds one past the highest existing V{seasonType}{year}P-NNNN across the whole season (the number itself carries no Assembly identity, only "Epic Link" does, so numbering is flat per season, not per Assembly), and clonePart copies the source Part's BOM fields into a fresh, unrelated ticket at that number, Revision A, no Build link. A cloned-but-unlinked Part still needs to be findable, so the hub's BOM also pulls in every Part under the Assembly via the existing epic-linked fetch, not just Build-linked ones — it shows up immediately as a Move/Re-create candidate. Also shipped: a Print button backed by a dedicated print-only BOM (the app's global print rules strip columns by position, which would have dropped Qty) and a Compare builds panel, derived entirely from the already-loaded part list. 438/438 tests passing, clean vite build. Assembly instructions authoring (steps + images in the Build's Instructions Data field) moves to Phase 5 with the rest of the authoring work; the print view will pick the steps up once they exist. A live-data smoke test against the real Jira instance confirmed the new read-only endpoints work, but found the team's current tickets (gearbox-practice Parts, template clones) predate this build season's naming convention — there's no real Assembly yet to click through end-to-end against, independent of anything in this plan.

  5. Phase 4

    Metadata round-trip

    Turn on updatePartMetadata/updateElementMetadata writes so repeat pastes resolve by stamped identity instead of name-matching.

  6. Phase 5

    Guidance, instructions authoring & polish

    The inline glossary and teaching empty states from Sheet 07; the instruction step editor with images; an activity log surfaced in the UI.

09

Decisions

The five judgment calls this plan raised, as settled by the team. Recorded here so the reasoning stays attached to the decision, not just the conclusion.

DecidedAnyone can create a Build. No lead gate — consistent with the team's existing preference for lightweight, confirm-but-don't-gate creation (Sheet 05's confirm dialog is a typo guard, not a permission check).
DecidedAnyone can start a Revision. Same answer as Build, even though revising a whole assembly is the bigger of the two calls — the team is choosing to trust students with it rather than route it through leads.
DecidedEvery Assembly starts at Revision A. Confirmed as the default from Sheet 02 — nothing changes for the majority of Assemblies, which are only ever on Revision A.
DecidedParts never span Assemblies. If the same design is needed under a different Assembly, that's a new Part number under that Assembly, not a shared link — the numbering scheme in Sheet 02 already assumed this. Within the same Assembly, a part carried into a later Revision only needs a new revision of itself if its design actually changed; reused unchanged, it's still just Revision A.
DecidedNo separate database — Jira holds it all. Detailed in Sheet 04 — issue links, attachments, a real workflow for Build status, and a structured field for instructions cover what a side database would have, with one accepted trade-off: Part quantity is one number per ticket, not one per Build it's used in.
